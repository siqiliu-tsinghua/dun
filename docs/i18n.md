# UI Text Internationalization

This document defines how `dun` translates its user interface text. The
approach was decided 2026-07-11 and recorded in TODO.md ("UI Text
Internationalization" stage); this document is the design of record.

## Model: compiled English, external translations

`dun` is a single-binary remote editing tool. The binary must keep working
alone on any host, and the 1 MiB release budget rules out compiling every
translation in. The model is therefore hybrid:

- **English is compiled in** as `&'static str` defaults. With no resource
  files present, `dun` behaves exactly as before: English UI, zero
  allocation, zero configuration.
- **Other languages are external resource files**, one file per language,
  loaded at runtime when the locale asks for one and the file exists.
  Missing files are not an error; the editor silently stays English.
- Only the loading mechanism and the English defaults count against the
  size budget.

UI label types use `Cow<'static, str>`: borrowed statics for the built-in
language, owned strings for loaded translations.

## Resource files

Translation files live in an `i18n/` directory next to the active config
file (`~/.config/dun/i18n/` under default discovery, or `<dir>/i18n/` when
the config comes from `--config <dir>/file` or `DUN_CONFIG`). With
`--no-config` the editor stays English.

**Two directories, in order.** A system-wide install has no per-user
directory to put files in, so the search continues into the installation
itself:

1. `i18n/` beside the active config file — yours, and always first;
2. `<bin>/../share/dun/i18n` — derived from `std::env::current_exe()`, so
   `/opt/dun/bin/dun` reads `/opt/dun/share/dun/i18n`, `/usr/bin/dun` reads
   `/usr/share/dun/i18n`, and `~/.local/bin/dun` reads
   `~/.local/share/dun/i18n`. Nothing is compiled in and no environment
   variable is involved: an administrator unpacks a prefix anywhere and it
   works, and a user who moves the binary moves its catalogs with it.

The order is by **directory, not by candidate**: the first directory that
has a file for any candidate of the locale answers, and a directory with
nothing for this locale is skipped. So your own `zh.conf` wins over a
system `zh-Hans.conf` even though the system file is the more specific tag
— what is yours wins as a set, which is the rule that can be stated in one
sentence. A file that exists but is broken is reported, never silently
replaced by the other directory's copy: a shared installation must not be
able to mask the file you installed yourself.

`--no-config` disables both, unchanged: it means built-in everything, and
that includes the built-in language. The Config Diagnostics window (`F6`)
prints the search path under **Paths**, so "why is my interface English"
is answerable without reading this document.

One file per language tag, named `<tag>.conf` (`zh-Hans.conf`, `de.conf`,
`ja.conf`, …; see Locale selection for how a tag is chosen). The format is the same line format as the main config file:

```text
# comment
menu.file = 文件
menu.file.new = 新建
```

Rules:

- UTF-8 only; `key = value` per line; `#` starts a comment; the value is
  the trimmed rest of the line, no quoting.
- Keys are lowercase `[a-z0-9._-]` (underscores appear where a key embeds
  a command id, e.g. `help.command.edit.move_left`). Unknown keys are
  ignored (a newer translation file must not break an older binary);
  duplicate keys follow config semantics (last wins).
- Values must be nonempty, at most 256 bytes, and must contain nothing the
  display sanitizer would escape: no control bytes, no ESC, no bidi
  formatting characters, no invisible zero-width characters. The check is
  the sanitizer itself (`DisplaySanitizer::sanitize_line` must return the
  value unchanged as pure text), so the rule can never drift from what the
  renderer enforces. Rendering still sanitizes chrome text afterwards —
  the load check is the first fence, not the only one.
- A file that violates the rules is rejected whole, with a line-numbered
  diagnostic in the status surface; the editor falls back to English.
  Files over 64 KiB are rejected before parsing.

## Locale selection

The language comes from the standard locale environment, first nonempty of
`LC_ALL`, `LC_MESSAGES`, `LANG`. The first candidate whose file exists wins;
`C`, `POSIX`, and empty values select English.

The candidate chain is region, then **script**, then bare language:

| locale | candidates |
| --- | --- |
| `zh_CN` / `zh_SG` / `zh_MY` | `zh-CN` → `zh-Hans` → `zh` |
| `zh_TW` / `zh_HK` / `zh_MO` | `zh-TW` → `zh-Hant` → `zh` |
| `zh` | `zh-Hans` → `zh` |
| `de_DE` | `de-DE` → `de` |

The script step exists because a Singaporean and a mainland reader use the
same Simplified characters, and nothing in `zh-SG` says so — script is the
fact that connects them, and it needs a (tiny) table. Shipped files are
therefore named by script (`zh-Hans.conf`), not by country: the name says
what the file *is*. The region tag stays first in the chain, so a user's own
`zh-CN.conf` still overrides the shipped file.

Deliberately **not** an alias table (`zh-SG → zh-CN`, as Microsoft Edit
does): which region is the "canonical" Simplified one is a product opinion,
and opinions do not belong in the core. Which script a region writes is not.

On ASCII-only terminals (`EncodingProfile::Ascii`) translations are not
loaded at all: non-ASCII text would only render as escaped code points
there, so English is strictly more readable.

## Menu mnemonics are invariant

Menu keyboard navigation is functional, not decorative: top-level items
take their mnemonic from the label's first letter ("File" → `F`), dropdown
entries from the trailing parenthesised letter ("Open... (O)" → `O`), and
mnemonics must stay unique within each menu. Translations must not be able
to break any of that, so:

- A translation supplies only the base text (`menu.file.new = 新建`),
  never the mnemonic.
- The code composes the visible label as `base (M)` where `M` is the
  mnemonic letter taken from the compiled English label. Translated menus
  render msedit-style — `文件 (F)`, `新建 (N)` — and every mnemonic keeps
  working identically in every language. Uniqueness holds by construction
  because the English set is unique (and tested).
- Top-level hit testing prefers a trailing parenthesised mnemonic when one
  is present and falls back to the first letter, so untranslated labels
  behave exactly as before.
- Plugin menus hold the same language-independence invariant, but the
  mnemonic is the **author's** to declare, not `dun`'s to derive. No general
  derivation rule survives a real plugin: an IDE host's `Find References` and
  `Format Document` both start with `F`. A host declares `top_mnemonic` and a
  per-item `mnemonic`; both are optional and both are one key for all
  languages. The full rule — character set, the top-level derivation that
  still applies when `top_mnemonic` is omitted, why an entry has *no*
  derivation, and the two different collision policies — lives in
  `docs/plugin-protocol.md` under "Menu mnemonics", since it is protocol
  surface rather than translation policy. What matters here is only that a
  translation never carries or changes a mnemonic: it supplies base text, and
  `dun` composes `base (M)` exactly as it does for its own menus.

## Slices

1. Mechanism + menus (landed 2026-07-13): catalog type and parser in
   `dun-config`, loading in `dun-cli`, `Cow` labels and composition in
   `dun-ui`, `i18n/zh-Hans.conf` shipped in the repo.
2. Help window (landed 2026-07-13): command descriptions are keyed by the
   command id (`help.command.edit.move_left`) so the key is stable and
   greppable; key-cap columns ("Enter", "Shift+Arrow") stay English —
   they are key names in every language. Two rules this slice
   established: enumerate every key in code
   (`help_translation_keys`) so a completeness test can fail with the
   exact missing list, and pad columns by display width, never char
   count — a translated cell can be wider than its char count says.
3. Dialog chrome (landed 2026-07-13): every translatable overlay string is
   declared once in `crates/dun-cli/src/ui_text/` as a
   `(key, English default)` pair, so keys have a single source and the
   completeness test enumerates them. This slice added the `{}` template
   rule: English defaults use positional `{}`, filled left to right, and a
   translation that needs a different word order uses **indexed** `{0}`,
   `{1}` instead (see "Reordering arguments" below). Either way a template
   whose arity does not match the English one is ignored in favor of
   English — a translation mistake must never drop a runtime value (the
   shipped-file test also rejects such mismatches outright). Confirmation
   button letters — `(s)`, `(d)`, `(c)`, `(r)`, `(a)` — are the keys the
   dialogs answer to; the code appends them and translations supply only
   the words, same invariant as menu mnemonics.
4. Status messages — the largest churn: scattered `format!` strings become
   parameterized templates (reusing `tr_fmt`), including the dialog
   event messages stored in state (`self.message`). Last on purpose.

Translations shipped in the repo `i18n/` directory are reference copies. The
editor never writes resource files — `scripts/install.sh` does that copy at
install time, into the installation's `<prefix>/share/dun/i18n`, and reports
which catalog the current locale selects; a user who wants to change one
copies that single file into their own `i18n/` beside their config, where it
takes precedence. Without that install step a fresh build is stuck in English
by omission, which is what the two-directory search path and the installer
exist to prevent.

### Translation provenance

State this plainly rather than as a promise: **nine of the ten shipped
catalogs are machine-translated and have not been reviewed by a native
speaker**, and neither has any key added since. There is no reviewer, so
"pending native-speaker review" was a queue that would never drain — it is
not tracked as outstanding work here.

What *is* enforced mechanically, and is worth relying on:
`every_shipped_translation_is_valid_and_complete` proves every catalog has
every key, the placeholder-shape checks reject a template that would drop or
reorder a `{}`, and the acceptance sweeps show no translated string overflows
80 columns. Correctness of *wording* is not checked by anything. Treat a
contribution correcting a translation as welcome and uncontroversial; the
mechanical gates will catch a structurally broken one.

## Validating a translation

Every `i18n/*.conf` file in the repository is validated by
`every_shipped_translation_is_valid_and_complete` (in
`crates/dun-cli/src/tests/i18n.rs`), which discovers the files rather than
naming them, so a new language is covered the moment it is added. Each file
must parse under the loader's rules, stay within the size cap, translate
**every** key the UI can look up (menus, help, dialog chrome, status), keep
each value's `{}` count equal to its English default's, and contain no keys
the UI never asks for. A failure lists exactly what is missing — that list is
how a translator finishes a file.

The three key sets are enumerated in code, not hand-maintained:
`ui_text::ALL`, `help::content::help_translation_keys()`, and
`dun_ui::menu_translation_keys()`. Each is derived from the same table its
renderer reads, so a key cannot exist in one and be missing from the other.

One check is not about completeness but about safety: `confirm.button.save`,
`confirm.button.discard` and `confirm.button.cancel` must be present and
**pairwise distinct**. Those words are drawn beside the literal `(s)`, `(d)`,
`(c)` keys the dialog answers to, so a translation that makes two of them read
alike invites a user to press `(d)` and lose unsaved work. Everywhere else the
vocabulary rule keeps a bad translation merely confusing; this is the one place
it could be destructive.

A **user-supplied** file is held to a lower bar on purpose: the runtime falls
back to English key by key, so a partial translation works. Only the
repository's own files must be complete.

## Reordering arguments

English defaults use positional placeholders, filled left to right:

```text
status.find.match = Find: {}/{} matches: {}
```

Some languages cannot say that in the English order — Japanese and Korean are
verb-final, and Russian word order is free. A translation may therefore use
**indexed** placeholders to put the arguments where its grammar wants them:

```text
status.find.match = 検索：{2} — {0}/{1} 件目
```

Rules, enforced by `indexed_template_is_valid` and by the shipped-translation
validator:

- a template is positional **or** indexed, never both;
- an indexed template must use every index in `0..arity` at least once (it may
  repeat one), and no index beyond that — skipping an argument would silently
  drop a runtime value, which is the whole thing the arity check exists to
  prevent;
- a template that breaks either rule is ignored and the English one renders
  instead, so a bad translation degrades to English rather than to nonsense.

Only 33 of the ~500 keys carry more than one placeholder, so most translations
never need this.

## Rules this stage established (read before adding translatable text)

These four rules are what make the translations safe to ship and cheap to
validate. New user-visible text must obey them, or it silently breaks a
language nobody on the team reads.

1. **Vocabulary the user types back stays English.** Command ids
   (`edit.move_left`), theme names (`msedit|turbo|dark|dun`),
   config-diagnostics tokens (`summary|paths|…`), key names (`Enter`,
   `Ctrl+X`), file paths: all are passed as `{}` arguments, never keyed. Only
   the prose around them translates. Menu mnemonics and confirm-button letters
   are the same rule applied to single characters — a translation must never
   change a string the user has to type back.

2. **Enumerate every key in code.** The three key sets — `ui_text::ALL`,
   `help::content::help_translation_keys()`, `dun_ui::menu_translation_keys()`
   — are each derived from the very table their renderer reads, so a key
   cannot exist in one and be missing from the other. This is what lets the
   validator fail with the exact list of missing keys, which is how a
   translator finishes a file. Text that is *inlined* at a call site instead
   of declared in a table cannot be enumerated, and the menus proved it: they
   were the one surface the validator could not see, and a shipped translation
   could have dropped a menu label with every test still green.

3. **Never store rendered English.** Store typed data and render where the
   catalog is in hand. `FileDialogState::message` and the dun-authored path
   errors both had to be un-stringified for this reason. When text must cross
   a boundary that carries no catalog (an `io::Error` through `io::Result`),
   use `io::Error`'s custom payload rather than churning signatures.

4. **One English source per string.** A `Display` impl that repeats an English
   default beside the key table is a second source that will drift, and it
   will drift silently, because tests read the same table the code does.
   `PathIoError::Display` and `exit_status_text` both render through the table
   with an empty catalog instead.

The one place a bad translation is *destructive* rather than merely confusing
is the unsaved-changes dialog, whose Save/Discard/Cancel words sit beside the
literal `(s)`/`(d)`/`(c)` keys it answers to. Undo and Cancel collapse into one
word in French, Italian and Russian, so this is not hypothetical. A test asserts
those three are present and pairwise distinct in every shipped file; keep it.
