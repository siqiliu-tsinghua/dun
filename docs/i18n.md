# UI Text Internationalization

This document defines how `dun` translates its user interface text. The
approach was decided 2026-07-11 and recorded in TODO.md ("UI Text
Internationalization" stage); this document is the design of record.

## Model: compiled English, external translations

`dun` is a single-binary remote editing tool. The binary must keep working
alone on any host, and the 1 MiB release budget rules out compiling every
translation in. The model is therefore hybrid:

- **English is compiled in** as `&'static str` defaults. With no resource
  files present, `dun` behaves exactly as before: English UI, zero
  allocation, zero configuration.
- **Other languages are external resource files**, one file per language,
  loaded at runtime when the locale asks for one and the file exists.
  Missing files are not an error; the editor silently stays English.
- Only the loading mechanism and the English defaults count against the
  size budget.

UI label types use `Cow<'static, str>`: borrowed statics for the built-in
language, owned strings for loaded translations.

## Resource files

Translation files live in an `i18n/` directory next to the active config
file (`~/.config/dun/i18n/` under default discovery, or `<dir>/i18n/` when
the config comes from `--config <dir>/file` or `DUN_CONFIG`). With
`--no-config` the editor stays English.

One file per language tag, named `<lang>.conf` (`zh-CN.conf`, `zh.conf`,
`de.conf`, …). The format is the same line format as the main config file:

```text
# comment
menu.file = 文件
menu.file.new = 新建
```

Rules:

- UTF-8 only; `key = value` per line; `#` starts a comment; the value is
  the trimmed rest of the line, no quoting.
- Keys are lowercase `[a-z0-9._-]` (underscores appear where a key embeds
  a command id, e.g. `help.command.edit.move_left`). Unknown keys are
  ignored (a newer translation file must not break an older binary);
  duplicate keys follow config semantics (last wins).
- Values must be nonempty, at most 256 bytes, and must contain nothing the
  display sanitizer would escape: no control bytes, no ESC, no bidi
  formatting characters, no invisible zero-width characters. The check is
  the sanitizer itself (`DisplaySanitizer::sanitize_line` must return the
  value unchanged as pure text), so the rule can never drift from what the
  renderer enforces. Rendering still sanitizes chrome text afterwards —
  the load check is the first fence, not the only one.
- A file that violates the rules is rejected whole, with a line-numbered
  diagnostic in the status surface; the editor falls back to English.
  Files over 64 KiB are rejected before parsing.

## Locale selection

The language comes from the standard locale environment, first nonempty of
`LC_ALL`, `LC_MESSAGES`, `LANG`. A value like `zh_CN.UTF-8` produces the
candidate list `["zh-CN", "zh"]`; the first candidate whose file exists
wins. `C`, `POSIX`, and empty values select English.

On ASCII-only terminals (`EncodingProfile::Ascii`) translations are not
loaded at all: non-ASCII text would only render as escaped code points
there, so English is strictly more readable.

## Menu mnemonics are invariant

Menu keyboard navigation is functional, not decorative: top-level items
take their mnemonic from the label's first letter ("File" → `F`), dropdown
entries from the trailing parenthesised letter ("Open... (O)" → `O`), and
mnemonics must stay unique within each menu. Translations must not be able
to break any of that, so:

- A translation supplies only the base text (`menu.file.new = 新建`),
  never the mnemonic.
- The code composes the visible label as `base (M)` where `M` is the
  mnemonic letter taken from the compiled English label. Translated menus
  render msedit-style — `文件 (F)`, `新建 (N)` — and every mnemonic keeps
  working identically in every language. Uniqueness holds by construction
  because the English set is unique (and tested).
- Top-level hit testing prefers a trailing parenthesised mnemonic when one
  is present and falls back to the first letter, so untranslated labels
  behave exactly as before.

## Slices

1. Mechanism + menus (landed 2026-07-13): catalog type and parser in
   `dun-config`, loading in `dun-cli`, `Cow` labels and composition in
   `dun-ui`, `i18n/zh-CN.conf` shipped in the repo.
2. Help window (landed 2026-07-13): command descriptions are keyed by the
   command id (`help.command.edit.move_left`) so the key is stable and
   greppable; key-cap columns ("Enter", "Shift+Arrow") stay English —
   they are key names in every language. Two rules this slice
   established: enumerate every key in code
   (`help_translation_keys`) so a completeness test can fail with the
   exact missing list, and pad columns by display width, never char
   count — a translated cell can be wider than its char count says.
3. Dialog chrome (landed 2026-07-13): every translatable overlay string is
   declared once in `crates/dun-cli/src/ui_text.rs` as a
   `(key, English default)` pair, so keys have a single source and the
   completeness test enumerates them. This slice added the `{}` template
   rule: a translation may reorder `{}` placeholders freely, but one whose
   placeholder count differs from the English template is ignored in favor
   of English — a translation mistake must never drop a runtime value (the
   shipped-file test also rejects such mismatches outright). Confirmation
   button letters — `(s)`, `(d)`, `(c)`, `(r)`, `(a)` — are the keys the
   dialogs answer to; the code appends them and translations supply only
   the words, same invariant as menu mnemonics.
4. Status messages — the largest churn: scattered `format!` strings become
   parameterized templates (reusing `tr_fmt`), including the dialog
   event messages stored in state (`self.message`). Last on purpose.

Translations shipped in the repo `i18n/` directory are reference copies;
users copy them next to their config. The editor never writes resource
files.
