# Brief 019 — The menu behaviour matrix: one golden table, all 40 entries

Implementation brief. Depends on the golden-file harness from brief 018.

When "Open... doesn't work" was reported, the only way to find out what each
menu entry actually did was to drive all forty by hand in tmux and eyeball the
screen. That audit found three separate bugs and then evaporated — it lives in a
scratch directory, not in the repo.

Make it permanent, and make it **self-maintaining**: the matrix is generated by
enumerating the menus, so a new entry appears in it the day it is added.

## Why a table and not forty screenshots

Forty full-screen goldens would be unreviewable and would churn on every
cosmetic change. What we actually want to pin is the *observable effect* of each
command: what modal opened, what the status line said, how many windows and
buffers exist afterwards. That fits on one line per entry, so the whole menu
surface is one reviewable table — and any behavioural change anywhere in it is a
one-line diff.

## Goal

A single golden file, `menu_matrix.txt`, with one line per menu entry, produced
by driving every entry from an identical starting state.

## Specification

### 1. The fixture state

Every entry is driven from the **same** freshly-built `AppState`, so the rows
are comparable:

- one window, one buffer, containing a small fixed text (e.g. three short
  lines), **not dirty**, with a stable file name (redact any absolute path — see
  brief 018's determinism rules).
- a fixed workspace area (e.g. `Rect::new(0, 0, 80, 24)`) via
  `sync_view_for_area`.

Build it fresh for each entry. State must not leak between rows.

### 2. Driving an entry

For each `(menu_index, entry_index)`, dispatch that entry's command through the
same path a user's keypress takes — open the menu and press the mnemonic, via
`handle_key_event`, so the matrix exercises the real dispatch and would have
caught the dead-mnemonic bug on its own.

Two entries need care:

- **`app.quit`** — safe: it sets `should_quit` (and may open the dirty confirm).
  Record it, do not special-case it away.
- **`app.shell_escape`** — it only *queues* a `RuntimeAction`; the event loop is
  what would spawn a shell, and there is no event loop in a unit test. Record the
  queued action. If you find it does anything else, STOP and report — that would
  be a real bug.

### 3. The row format

One line per entry, columns padded so the table reads straight down:

```text
menu  entry  label                  command              win buf  modal            status
File  New (N)                       file.new              1   1   -                "New untitled buffer"
File  Open... (O)                   file.open             1   1   Open             -
File  Switch Buffer (B)             file.switch_buffer    1   1   -                "Buffer switcher: only one buffer"
…
View  Split Horizontal (H)          window.split_horiz…   2   2   -                "Split horizontally"
```

- `modal` names whichever of `file_dialog` / `prompt` / `confirm` /
  `buffer_switcher` is open afterwards (its kind or title), or `-`.
- `status` is `status_message`, quoted, or `-` when none. This column is what
  pins the "commands report what they did" behaviour that was silently broken.
- Add a `quit` column, or a trailing marker, for `should_quit`, and a
  `runtime` column for a queued `RuntimeAction`. Only show them when non-empty.
- Truncate nothing that carries meaning; widen the column instead.
- Header line, then a row per entry, grouped by menu in menu order.

### 4. What the test asserts

Just `assert_snapshot("menu_matrix", table)`. The oracle is the human review of
the golden, once. That is the point: it turns "did somebody check that Save
still says something?" into a diff.

## dun pitfalls (read twice)

1. **Safe Rust is forbidden-unsafe.** `#![forbid(unsafe_code)]` is in force.
2. **The 1 MiB size budget is real**, though this brief is test-only.
3. **Enumerate, do not hardcode.** A hand-written list of forty entries is a
   list that will drift — the same failure that let forty dead mnemonics survive.
4. **A golden must be reproducible on another machine** — no absolute paths, no
   timestamps. See brief 018's determinism rules.
5. **The golden records reality, not the ideal.** If a command misbehaves, the
   golden shows the misbehaviour and the report names it. Silently "fixing" the
   table is the worst possible outcome: it would make the matrix bless a bug
   forever.
6. **`dun-cli` is a binary crate** — the test goes in `src/tests/`.
7. **Stop-loss is real.** If the same step fails twice for the same reason,
   STOP and report.
